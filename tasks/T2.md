### reza-phys/conductor — exists, pushed 2026-10-06
Multi-agent orchestration harness; plans + nested dispatch + audit gates + provenance + live dashboard, enforced via hooks (not model requests).
- Copy: event-sourced state — hooks append every op (reads/commands/writes/claims/verdicts) to append-only `.conductor/events.jsonl`; an incremental cache replays events (~50ms/hook) instead of holding mutable state. Good pattern for crash-safe, resumable dashboards.
- Copy: `PreToolUse` validates dispatch envelopes (`<conductor-task>` XML) and enforces depth limits; `SubagentStop` gates — blocks the report until sub-agent finishes, claims verified, evidence matches observations. Maps to our `tool.call`/`agent.spawn` hooks.
- Copy: reconstructs agent hierarchy from parent/child agent_id links in `PostToolUse` payloads — relevant since our API also exposes `agent.spawn`/`$.agent.list`.
- Copy: dashboard (`dashboard/`, `.conductor/status.json`/`status.html`) regenerates from the event log with no LLM call — cheap, deterministic render.
- Avoid: requires XML envelope dispatch protocol (`<conductor-task>`) — heavier than our plugin API's native `$.agent.spawn({subagentType})`; don't replicate the custom envelope, use the real tool.
- Files: `src/conductor/cli.py`, `dashboard/`, `.conductor/config.json`, `.conductor/events.jsonl`, `.conductor/plans/`.

### xuanji86/claude-agentpane — exists, pushed 2026-10-04 (updated 2026-10-05)
Side pane showing subagents of a session: status, model, tokens (in/out/cached), elapsed time, nested hierarchy, click-through to transcript, stop button.
- Copy: state source is exactly our plugin API — `$.agent.list()` + `agent.spawn` events for the roster, `tool.call` for activity, `turn.step` for token/stop-reason, `$.session.messages({agentId})` to open a transcript on click. This is the direct template for our agent-roster pane (matches `pane.tsx`/`$.ui.render` pattern from plugin-authoring examples).
- Copy: hooks "pass events on unchanged" (always calls `next(e)`) except when the user explicitly triggers stop (presumably via `TaskStop`) — read-only observation, no interference with normal flow.
- Copy: zero persistence — no files/network/process, nothing stored across sessions; pane state lives in-memory (atom) only, rebuilt each session. Simpler than conductor's event log; fine for a UI-only mod with no cross-session need.
- Avoid: nothing notable to avoid; it's a clean minimal pattern.
- Files: `hooks/` (hook implementations), `types/`, `.claude-plugin/plugin.json`. Requires Claude Code 2.1.287+ (we're targeting 2.1.289, compatible).

### muellerei/task-line — exists, pushed 2026-10-05
One-line task-progress band above the prompt (terminal + desktop), showing current task, progress bar, count/percentage, status notes.
- Copy: hooks `TodoWrite`/`TaskCreate`/`TaskUpdate` tool calls (plus a `work_state_write` MCP tool) to source task-list state, rather than parsing chat text — same idea as agentpane's `$.agent.list`/`tool.call` approach, applied to todos instead of agents.
- Copy: uses `Bash` tool-call interception to detect failing tests/builds and surface "check names in red" — a nice pattern for status derived from command exit, reusable for dashboard health indicators.
- Copy: caps in-memory history (20 recent lists), fades finished lists after a configurable `lingerSeconds`, manual hide via × — good UX precedent for a status band that shouldn't accumulate forever.
- Avoid (important gotcha): explicitly notes that a band drawn above the prompt which doesn't call `next(e)` will hide another mod's band output if both target the same `AbovePrompt` region — i.e. two `ui.render`/`AbovePrompt` hooks fighting unless each respects the chain. If T3 builds both a pane and a band, make sure the band hook always calls `next(e)` so it composes with others (confirmed also by the plugin-authoring `band.tsx` example which calls `next(e)` when quiet).
- Files: `register.tsx` (band rendering + command dispatch), `layout.ts`, `cells.ts`, `lists.ts`, `config.ts`, tests (`units.test.ts`, `boundaries.test.tsx`, `register.test.tsx`).

### Local API reference (plugin-authoring skill, bundle 2.1.289)
- `reference.md` confirms the hook contract: `on(event, matcher?, hook)`, `($, e, next)`, `$.agent.register`/`$.agent.spawn({subagentType})`, `$.tool.register` + `tool.call` matcher `{tool:'mcp__<plugin>__<name>'}`, `$.command.register`, `$.ui.open`/`$.ui.render`/`$.ui.toast`.
- `examples/pane.tsx` + `pane-state.d.ts`: canonical pane pattern — `atom({plugin,key}, default)` + `read`/`update` for state, `on('tool.call', ...)` wraps `next(e)` to track start/done, `on('ui.render', {component:'Pane', requestId})` renders via `$.ui.resolve(e)` (`Box`/`Text`). This is the template to follow for an agent-roster/dashboard pane — matches what claude-agentpane does conceptually.
- `examples/band.tsx`: `AbovePrompt` band pattern — tracks `startedAt`/`tools` across `prompt.submit`→`tool.call`→`turn.complete`, calls `next(e)` when quiet (critical per task-line's warning above), toasts on slow turns.

## Cross-repo summary: what to copy into T3
1. Use `$.agent.list()`/`agent.spawn`/`turn.step`/`tool.call` (agentpane's exact approach) as the state source for an agent/task roster — don't invent a custom envelope protocol (avoid conductor's XML dispatch layer; use native `$.agent.spawn`).
2. For any state needing cross-session durability, use an append-only event log + replay cache (conductor's `.conductor/events.jsonl` pattern) rather than ad hoc mutable state; for pane-only UI state, in-memory atoms are sufficient and simpler (agentpane's choice).
3. Always call `next(e)` in `AbovePrompt`/band hooks unless deliberately suppressing, to avoid clobbering other mods' bands (task-line's documented gotcha, matches `band.tsx` example).
4. Derive health/status indicators from `Bash`/tool-call exit results (task-line) rather than re-parsing transcript text.
5. Gate/audit logic (conductor's `SubagentStop` claim-verification gate) is a heavier pattern — worth noting as a possible future feature but likely out of scope for an initial T3 build.
